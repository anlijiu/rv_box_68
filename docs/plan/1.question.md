
## User

问几个问题                                                           
1. 现在不用 PartDesign::Body + Sketch + Pad 是因为没有真实零件尺寸？
2. 现在本计划可以加上 Assembly4 LCS 约束 么？ 
3. 现在本计划可以子系统拆分为独立 FCStd 文件么？

---

## Codex

1. **基本是，因为当前没有真实零件尺寸，但不止这个原因。**

当前 plan 用 `Part::Box`，主要原因是它处在“装配骨架/层级验证”阶段，而不是“真实零件建模”阶段。

`PartDesign::Body + Sketch + Pad` 更适合真实零件建模，因为它需要至少明确这些信息：

- 零件的真实尺寸，或者近似尺寸
- 草图所在平面
- 拉伸方向和厚度
- 零件局部坐标原点
- 与父总成、相邻零件之间的定位基准
- 后续是否需要孔、倒角、圆角、开槽、布尔运算等特征

现在的 `Part::Box` 是占位几何，优点是：

- 创建简单，脚本更可靠
- 立即可见
- 适合检查层级、命名、BOM 属性、颜色、坐标布局
- 不需要为每个零件定义草图和特征历史

所以准确说：**不是 PartDesign::Body 不适合，而是当前阶段还没有足够的几何/制造信息，直接上 Body + Sketch + Pad 会增加复杂度，但不会提高装配结构的正确性。**

等你开始给每个零件补真实尺寸时，就可以逐步替换：

```text
Part::Box placeholder
→ PartDesign::Body
→ Sketch
→ Pad
→ Hole / Pocket / Fillet / Chamfer
→ LCS / constraints
```

建议不要一次性把 69 个 `Part::Box` 全换成 Body。更稳的是先挑一个子系统，比如 `WaterSystem` 或 `CargoBox`，验证 Body 建模流程和装配定位流程，再推广。

2. **可以加 Assembly4 LCS 约束，但现在不建议马上加“完整约束”；可以先加 LCS 基准点。**

当前 plan 可以作为 Assembly4 的前置骨架，因为已经具备几个必要条件：

- 有清晰的 `App::Part` 层级
- 每个 assembly/body 都有稳定名称
- 子系统已经分层
- 每个对象有初始 Placement
- 文档为空运行，结构可重复生成

但要真正做 Assembly4 约束，还需要更明确的定位语义。Assembly4 的核心不是“把东西放在某个 X/Y/Z 网格上”，而是用 LCS 表达装配基准，例如：

```text
RV_Asm
├── LCS_Chassis_Mount
├── LCS_CargoBox_Mount
├── LCS_WaterSystem_Zone
└── ...
```

以及子系统内部：

```text
Chassis
├── LCS_Frame_Origin
├── LCS_Front_Axle
├── LCS_Rear_Axle
├── LCS_Fuel_Tank_Mount
```

当前 plan 的 Placement 网格是“可视化布局”，不是工程装配定位。它能防止占位方块重叠，但不能代表真实装配约束。

所以建议分两阶段：

**阶段 A：可以现在加的**

给每个 `App::Part` 添加一个默认 LCS，作为未来约束锚点：

```text
RV_Asm
Chassis
Powertrain
CargoBox
WaterSystem
...
```

每个 assembly 至少有：

```text
LCS_Origin
```

一级子系统可以有：

```text
LCS_Mount
LCS_Service
LCS_Interface
```

这一步可以现在加，因为不依赖真实零件尺寸，只是建立接口位置的占位基准。

**阶段 B：暂时不要完整做的**

暂时不要急着做精确 Assembly4 约束，例如：

- 底盘和厢体真实安装点
- 水箱支架定位
- 管路接口定位
- 电气线束路径
- 家具与地板/墙体的真实安装关系
- 门窗与墙体开孔的约束关系

这些需要真实尺寸、坐标基准、安装面、孔位或接口定义。否则 LCS 会变成“看起来有约束，但实际没有工程意义”的占位数据。

结论：**可以把 Assembly4 LCS 加进 plan，但建议加成“LCS 基准/接口占位”阶段，而不是马上做完整约束系统。**

可以在 plan 里新增一节：

```text
Step 5: 添加 Assembly4 LCS 占位基准
- 为每个 App::Part 添加 LCS_Origin
- 为一级子系统添加 LCS_Mount
- 暂不建立精确约束表达式
- 后续根据真实尺寸替换 Placement 网格为 Assembly4 约束定位
```

3. **可以拆分为独立 FCStd 文件，但现在建议先别拆；至少要等主装配树跑通并冻结命名规则之后。**

从结构上看，当前 plan 已经具备拆分条件：

```text
RV.FCStd
├── Chassis.FCStd
├── Powertrain.FCStd
├── CargoBox.FCStd
├── Interior.FCStd
├── Furniture.FCStd
├── Bathroom.FCStd
├── WaterSystem.FCStd
...
```

但是拆分独立 FCStd 会带来几个新的复杂点：

- 文件之间如何引用
- 子系统文件如何保持稳定命名
- 主装配如何加载外部子系统
- Assembly4 link / App::Link 如何组织
- BOM 是在总装导出，还是各子系统导出后合并
- 修改子系统后主装是否自动更新
- LCS 是否跨文件对齐
- 子系统坐标原点如何定义

当前 plan 还在“单文件骨架验证”阶段。如果现在就拆，调试成本会上升很多。比如一个对象没显示，你需要判断是：

```text
子系统文件没生成？
外部链接没加载？
App::Link 路径错了？
LCS 没对上？
Placement 被父级覆盖？
BOM 属性在源对象还是 Link 对象上？
```

所以建议顺序是：

```text
阶段 1：单文件 RV.FCStd
- 创建完整树
- 验证 50 assemblies / 69 bodies / 119 total
- 验证 Placement 和颜色
- 验证 BOM 属性

阶段 2：单文件中加入 LCS 占位
- 每个子系统有稳定 LCS_Origin
- 一级子系统有 LCS_Mount
- 验证坐标基准

阶段 3：拆分子系统 FCStd
- 每个一级子系统保存为独立文件
- 主 RV.FCStd 用 App::Link / Assembly4 link 引用
- 主装只负责顶层布局和跨系统接口

阶段 4：真实几何替换
- 子系统文件内部把 Part::Box 替换为 Body + Sketch + Pad
- LCS 绑定到真实安装面/孔位/接口
```

也就是说：**可以拆，但最好不要现在拆。先单文件跑通，再拆。**

如果你现在就想把拆分能力写进 plan，可以写成“后续阶段”，不要把它并入 Step 2 的首版脚本。当前 Step 2 已经够大了，继续塞文件拆分会让失败面变大。

推荐新增一节：

```text
## 阶段化路线

### Phase 1: 单文件骨架
生成 RV.FCStd，包含完整 App::Part / Part::Box 层级。

### Phase 2: LCS 占位
在单文件中为 assembly 添加 LCS_Origin / LCS_Mount，占位表达装配接口。

### Phase 3: 子系统拆分
将一级子系统导出为独立 FCStd，并在 RV.FCStd 中用 App::Link / Assembly4 link 引用。

### Phase 4: 真实零件建模
将 Part::Box 替换为 PartDesign::Body + Sketch + Pad，并用真实 LCS 约束定位。
```

---

**直接回答**

1. **是的，主要因为现在没有真实零件尺寸和建模基准，所以先不用 `PartDesign::Body + Sketch + Pad`。** 当前 `Part::Box` 是为了验证装配层级、命名、统计、BOM 和可视化布局。

2. **可以加 Assembly4 LCS，但建议现在只加 LCS 占位基准，不要做完整精确约束。** 完整约束需要真实安装点、接口坐标和零件尺寸。

3. **可以拆成独立 FCStd，但建议等单文件骨架和 LCS 基准跑通后再拆。** 当前阶段先保持单文件更利于调试；拆分应作为 Phase 3。
